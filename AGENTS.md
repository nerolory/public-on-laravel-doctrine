# Правила проекта

## Границы задачи

- Запросы «посмотри», «проверь», «узнай» означают сбор информации без изменения проекта.
- Выполняй только указанную задачу. Коммиты и чекпоинты создавай только по отдельной просьбе пользователя.
- При работе с Laravel Doctrine опирайся на документацию соответствующих установленных версий; предположения отмечай отдельно.

## Архитектура

- Для работы с пользователями соблюдай цепочку `UserController → UserService → UserRepository`; запросы к базе находятся в репозитории.
- Action-классы в текущей архитектуре используются для регистрации и авторизации.
- Используй существующие сущности Doctrine и не создавай дублирующие Eloquent-модели.
- Прежде чем добавлять код, проверь возможность повторного использования существующих компонентов. Соблюдай DRY.
- Внедряй зависимости явно; не создавай скрытые циклические зависимости между сервисами.

## PHP и данные

- Для новых PHP-файлов используй `declare(strict_types=1)` и указывай типы параметров и возвращаемых значений.
- Используй DTO для передачи связанных данных между слоями, когда это соответствует задаче.
- Не привязывай бизнес-логику к случайным числовым идентификаторам записей; предпочитай стабильные бизнес-ключи.
- Не помещай запросы к базе в контроллеры; избегай N+1 и используй пагинацию для списков.

## Безопасность и проверка

- Проверяй права доступа на сервере и валидируй входные данные; пользовательский ввод передавай в запросы параметрами.
- Для публичных операций записи учитывай ограничение частоты запросов.
- Проверяй изменения подходящими тестами, не затрагивающими пользовательские данные. Для Doctrine используй изолированную тестовую базу.
