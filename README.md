# Слова и смыслы

Приложение со статьями и личным кабинетом. Публичный интерфейс работает на Nuxt 4, серверная часть — на Laravel 12 и Laravel Doctrine. Админка использует MoonShine 4 и работает с Doctrine через сервисы и репозитории.

## Что здесь показано из Doctrine

| Возможность | Где |
| --- | --- |
| Встраиваемые объекты (`#[Embeddable]`) | `PersonName` (ФИО в `users`), `ImageDimensions`, `SeoMeta` (колонки `seo_*` у статей и разделов) |
| Наследование одной таблицей (`SINGLE_TABLE`) | реакции `ArticleReaction` / `CommentReaction`, жалобы на статью, комментарий, пользователя и альбом |
| Перечисления PHP в колонках (`enumType`) | `ModerationStatus`, `ReactionType`, `ComplaintReason`, `ChartType`, `Gender`, `ConsentType` |
| Связи | многие-ко-многим со своей таблицей (разделы, теги, выбор в бюллетене), один-ко-многим с `orderBy` и `orphanRemoval` (варианты опроса, фото альбома), один-к-одному (опрос статьи), ссылка на себя (ветки комментариев, дерево разделов) |
| Оптимистическая блокировка | `#[ORM\Version]` у статьи и `LockMode::OPTIMISTIC`: конфликт правок даёт 409 |
| Расширения Gedmo | Tree (nested set) и Sluggable у разделов, Timestampable, SoftDeleteable (архив статей), Loggable со своей сущностью журнала на `json` |
| SQL-фильтры | `active_users` скрывает удалённые учётные записи во всех запросах, `soft-deleteable` — архивные статьи |
| Подписчик событий | `CacheInvalidationSubscriber` собирает изменения в `onFlush` и сбрасывает кеш в `postFlush` |
| Неизменяемые сущности (`readOnly`) | версии правовых документов, журнал согласий, графики, сырые просмотры |
| DQL | выборки сразу в массивы, fetch join без N+1, пути к полям встраиваемых объектов, агрегаты с `CASE` и `HAVING`, произвольные `JOIN ... WITH`, массовые `UPDATE` и `DELETE`, `LIKE ... ESCAPE` |
| DBAL там, где DQL не хватает | оконная функция `ROW_NUMBER()` для последних голосов, группировка по дням для статистики, вставка просмотра, не закрывающая EntityManager при повторе |
| Миграции | генерируются `doctrine:migrations:diff`; смена структуры данных — в два этапа с сидером между миграциями |

## Контейнеры

| Сервис | Назначение |
| --- | --- |
| frontend | Nuxt 4, доступен через nginx |
| nginx | Публичный сайт и MoonShine, http://localhost:8080 |
| app | PHP-FPM и Laravel |
| worker | Обработчик очередей Redis |
| scheduler | Планировщик Laravel: ночная пересборка карты сайта и очистка сырых просмотров старше полугода |
| postgres | PostgreSQL 17 |
| redis | Кэш, сессии и очередь |

Конфигурация Compose предназначена для локальной разработки; Nuxt запущен в режиме разработки, адреса портов доступны только на локальном компьютере. Адрес API, к которому Nuxt обращается при отрисовке на сервере, задаёт переменная `NUXT_API_UPSTREAM` (в Compose — `http://nginx`).

## Запуск

Нужен Docker с Compose. Из корня проекта:

```powershell
Copy-Item .env.example .env # Только если .env ещё нет
docker compose build app
docker compose up -d
docker compose exec app php artisan key:generate # Только для нового окружения
docker compose exec app php artisan doctrine:migrations:migrate --no-interaction
docker compose exec app php artisan db:seed --class=RoleSeeder --no-interaction
docker compose exec app php artisan db:seed --class=LanguageSeeder --no-interaction
docker compose exec app php artisan db:seed --class=LegalDocumentSeeder --no-interaction
docker compose exec app php artisan db:seed --class=SettingsSeeder --no-interaction
docker compose exec app php artisan db:seed --class=ArticleSectionSeeder --no-interaction
docker compose exec app php artisan vendor:publish --tag=laravel-assets --force
docker compose exec frontend npm run build:admin
```

Первый запуск Nuxt устанавливает зависимости из `frontend/package-lock.json`. Публичный сайт доступен на http://localhost:8080/, а админка — на http://localhost:8080/admin. API использует тот же адрес с префиксом `/api`.

Для схемы используются миграции Doctrine из `database/doctrine-migrations`. Не запускайте стандартные Laravel-миграции для этой базы: они повторно создают таблицы, управляемые Doctrine.

Для обновления базы со старым полем `user_permissions.is_admin` переход нужно выполнить поэтапно, не запуская все миграции сразу:

```powershell
docker compose exec app php artisan doctrine:migrations:migrate 'Database\DoctrineMigrations\Version20261029205941' --no-interaction
docker compose exec app php artisan db:seed --class=LegacyPermissionSeeder --no-interaction
docker compose exec app php artisan doctrine:migrations:migrate --no-interaction
```

Первый этап сохраняет существующие статьи опубликованными; сидер переносит прежние права администратора в назначенные роли. Для существующей базы выполняйте этот переход до применения последующих миграций.

Раздел статьи раньше хранился в колонке `articles.section_id`, теперь связи лежат в таблице `article_section_links`. Для базы, где колонка ещё есть, переход тоже выполняется поэтапно: миграция создаёт таблицу связей, сидер копирует в неё прежние разделы, следующая миграция удаляет колонку.

```powershell
docker compose exec app php artisan doctrine:migrations:migrate 'Database\DoctrineMigrations\Version20261029232938' --no-interaction
docker compose exec app php artisan db:seed --class=ArticleSectionLinkSeeder --no-interaction
docker compose exec app php artisan doctrine:migrations:migrate --no-interaction
```

Имя пользователя раньше хранилось в колонке `users.name`, теперь — в ФИО из трёх полей. Для базы, где колонка ещё есть, переход тоже поэтапный:

```powershell
docker compose exec app php artisan doctrine:migrations:migrate 'Database\DoctrineMigrations\Version20261030024224' --no-interaction
docker compose exec app php artisan db:seed --class=ProfileNameSeeder --no-interaction
docker compose exec app php artisan doctrine:migrations:migrate --no-interaction
```

Если база старше нескольких переходов, выполните их по порядку: права, разделы, имя. Сидер связей ничего не делает, когда колонки `articles.section_id` уже нет, поэтому для новой базы он не нужен.

Статьи, написанные до появления редактора, хранились простым текстом, а дата публикации появилась позже самих статей. Графики раньше хранились в тексте картинкой со ссылкой `data-chart`, теперь — блоком `figure` с этой ссылкой. После миграций переведите текст в HTML, графики в блоки и заполните даты публикации (все три сидера можно запускать повторно):

```powershell
docker compose exec app php artisan db:seed --class=ArticleHtmlContentSeeder --no-interaction
docker compose exec app php artisan db:seed --class=ArticleChartBlockSeeder --no-interaction
docker compose exec app php artisan db:seed --class=ArticlePublishedAtSeeder --no-interaction
docker compose exec app php artisan cache:clear
```

Ассеты админки — общие стили и модерация в списках (`frontend/editor/admin.ts`) и редактор формы статьи (`frontend/editor/article-editor.ts`, тот же модуль, что и на сайте) — собираются Vite с манифестом в `public/build/admin` (каталог не хранится в git). Страницы MoonShine подключают их через `Illuminate\Foundation\Vite`. Соберите их после установки и после правок в `frontend/editor`:

```powershell
docker compose exec frontend npm run build:admin
```

## Админка

MoonShine доступен на http://localhost:8080/admin. Роли хранятся в `roles`, назначения — в `user_permissions`. Роль `user` предоставляется всем автоматически; дополнительные роли можно назначать на странице пользователей в админке. В админку допускаются модератор, администратор и владелец.

Назначить первоначального владельца из существующих пользователей можно через Tinker после заполнения таблицы ролей:

```powershell
docker compose exec app php artisan tinker
```

```php
$user = app(App\Contracts\UserRepository::class)->findByEmail('email@example.com');
app(App\Repositories\UserPermissionRepository::class)->grant($user, App\Entities\Role::OWNER);
```

Вместо `email@example.com` укажите email существующей учётной записи и убедитесь, что она найдена до назначения роли.

Автор создаёт статью на странице `/write`, она уходит на модерацию. Модератор, администратор или владелец публикует её в админке или отклоняет с обязательной причиной; публичная часть показывает только опубликованные статьи. В админке также модерируются альбомы, разбираются жалобы, а владельцу и администраторам доступен «Рейтинг конфликтности».

Главная страница админки показывает метрики и авторов с наибольшим числом статей (сколько — задаётся в настройках, группа «Списки»). В рейтинге учитываются опубликованные статьи и черновики; удалённые пользователи исключены. Результаты кэшируются на одну минуту.

## Разделы статей

Разделы образуют дерево произвольной глубины. Дерево хранится по схеме nested set с помощью Tree из `gedmo/doctrine-extensions`, которое подключает `laravel-doctrine/extensions`. Ключ раздела в адресе создаёт Sluggable из того же пакета.

Статья может входить в любое число разделов, в том числе в раздел и его подраздел одновременно. Связи хранятся в таблице `article_section_links`. Автор выбирает разделы на странице `/write`, модератор — в редакторе статьи в админке.

Разделами управляют модератор, администратор и владелец на странице «Разделы статей» в админке:

- карандаш открывает форму, где меняются название, ключ в адресе и родительский раздел; ключ проверяется на уникальность, после его смены старые ссылки на раздел перестают работать;
- раздел можно перенести в любой другой, кроме него самого и его подразделов;
- корзина удаляет раздел: его статьи получают родительский раздел, подразделы поднимаются на уровень выше;
- корневой раздел удаляется, только если в нём нет подразделов и статей; до этого корзина неактивна.

`ArticleSectionSeeder` создаёт разделы по умолчанию и раскладывает по ним демонстрационные статьи по заголовкам. Статьи, у которых уже есть хотя бы один раздел, сидер не меняет, поэтому его можно запускать повторно.

На главной странице есть фильтр по разделам; по умолчанию выбрано «Все». Для выбранного раздела с подразделами появляется следующий ряд кнопок, по одному ряду на уровень. Выбранный раздел хранится в адресе, например `/?section=razrabotka`. Фильтр по разделу показывает и статьи всех его подразделов. API принимает тот же параметр: `/api/articles?section=razrabotka`.

## Настройки сайта

Настройки хранятся в таблице `settings` и меняются в админке на странице «Настройки»; доступ есть у владельца и администратора. Значения кешируются целиком и сбрасываются подписчиком Doctrine `CacheInvalidationSubscriber` после сохранения. Группы и поля описаны в `app/Services/Settings/SettingsSchema.php`: форма, проверка и значения по умолчанию строятся из этого описания. `SettingsSeeder` добавляет отсутствующие ключи и заполняет пустые обязательные значения (адрес и имя отправителя почты), сохранённые значения не меняет; запускать его можно повторно.

- **Публикации.** Лимиты контента: картинок в статье, тегов, фото в альбоме, вариантов опроса, длина комментария, строк и рядов графика, порог автоскрытия по жалобам.
- **Списки.** Размеры страниц: лента, комментарии, альбомы, проголосовавшие, списки и рейтинги админки, топы статистики, подсказки тегов, RSS.
- **Статистика.** Срок хранения сырых просмотров.

Лимиты форм вместе с длинами полей сущностей фронтенд получает из `/api/site` (поле `limits`), админка — из атрибута `data-limits` редактора, поэтому числа не дублируются в коде интерфейса.

- **Почта.** Адрес и имя отправителя обязательны. Если отправка через SMTP выключена, письма пишутся в журнал. Кнопка «Отправить тестовое письмо» проверяет сохранённые настройки.
- **Файлы.** Картинки приводятся к WebP в нескольких ширинах и хранятся в `public/media` или в S3-совместимом хранилище. Хранилище выбирается в настройках; уже загруженные файлы остаются там, куда были записаны.

## Языки

Интерфейс переведён на русский и английский: фразы бэкенда и админки лежат в `lang/{ru,en}/*.php`, тексты публичной части — в `lang/{ru,en}/front.php`. Фронт получает их через `/api/i18n/{code}`. Русский перевод интерфейса MoonShine — в `lang/vendor/moonshine/ru`, английский поставляется с пакетом.

Языки добавляются в админке на странице «Языки»: список языковых файлов строится по папкам в `lang/`. Режим мультиязычности выбирается в настройках: один язык, префикс в адресе (`/en/`) или поддомен (`en.example.com`). Тест `LocalizationTest` проверяет, что у русского и английского файлов одинаковый набор ключей.

## Регистрация и согласия

Правила регистрации зависят от региона в настройках (группа «Правовой режим»): Россия (152-ФЗ), ЕС (GDPR) или США (CCPA, COPPA). Каждый регион — отдельная стратегия в `app/Services/Legal/Policies`: она задаёт обязательные и добровольные согласия, минимальный возраст, баннер cookies и выгрузку данных. Новый регион добавляется новым классом.

Тексты документов редактируются в админке на странице «Правовые документы». Каждое сохранение создаёт новую версию, старые хранятся. Журнал `consents` только дополняется: в нём пользователь, версия текста, `is_agree`, время, IP и браузер. Если вышла новая версия обязательного документа, публиковать статьи и картинки нельзя, пока пользователь её не примет: API отвечает 409, сайт показывает окно с новым текстом.

Согласия на обработку персональных данных и с правилами сайта отзываются только при удалении учётной записи, рассылки и cookies — в личном кабинете. Принять или отозвать можно только согласие, документ которого опубликован в текущем регионе: остальные виды запрос отклоняет ошибкой 422 (например, согласия на cookies в США). Тексты в `LegalDocumentSeeder` — заглушки, их нужно заменить на подготовленные юристом.

## Профиль и вход

Профиль хранит ФИО (встраиваемый объект Doctrine `PersonName`), дату рождения, пол, «о себе», контакты, соцсети и аватар. Видимость каждого поля пользователь выбирает сам, по умолчанию всё скрыто; без видимого ФИО публично показывается часть email до «@». Публичная карточка автора — `/authors/{id}`.

После регистрации и смены email уходит письмо со ссылкой подтверждения, действующей сутки. Владелец сайта не может удалить свою учётную запись: удаление доступно через отдельный интерфейс `AccountSelfDeletion`, и для владельца он отказывает.

Вход через VK ID, Яндекс ID, Google, Apple, Facebook и Telegram включается в настройках (группа «Вход через соцсети»). Адрес возврата для OAuth-провайдеров — `/api/auth/{провайдер}/callback`; для Telegram нужно указать домен сайта боту командой `/setdomain`. Учётная запись связывается по email; новому пользователю сначала показываются обязательные согласия, а при входе через Telegram ещё и запрашивается email.

## Статьи и работа автора

Сущность `Article` показывает несколько возможностей Doctrine и Gedmo: `Timestampable` ведёт даты, `SoftDeleteable` превращает удаление в архив (статья пропадает с сайта, но остаётся в базе), `Loggable` пишет версии заголовка, текста и статуса в `article_log_entries` — своя сущность журнала с полем `json`, потому что поставляемая использует тип `array`, которого нет в DBAL 4. `#[ORM\Version]` даёт оптимистическую блокировку: если статью изменили, пока форма была открыта, сервер отвечает 409, а сайт предлагает загрузить актуальную версию.

На странице «Мои статьи» (`/my-articles`) автор видит свои статьи по статусам и причину отклонения. Правка (`/my-articles/{id}`) отправляет статью на повторную модерацию; удаление требует причину и переносит статью в архив. Неопубликованную статью видят только автор и модераторы. Краткое описание — до 160 символов; если оно пустое, анонсом служит начало текста с многоточием на ту же длину. Анонс считает сервер.

Теги задают автор и модератор: можно выбрать существующий или создать новый, «PHP» и «php» — один тег. Страниц у тегов нет — они нужны для meta keywords и `article:tag`.

## Редактор

Редактор на TipTap 3 написан без привязки к фреймворку (`frontend/editor/rich-editor/`: узлы, панель, окна вставки, таблица графика): на сайте его оборачивает компонент Vue, в админке работает сборка `public/build/admin` (`frontend/editor/article-editor.ts`). Поддерживаются заголовки, списки, цитаты, код, ссылки, таблицы, картинки (число задаётся в настройках), графики, альбомы и обложка.

Сервер принимает только разрешённый HTML (`symfony/html-sanitizer`, белый список тегов) и хранит его в каноническом виде: картинки — ссылками `data-image`, графики и альбомы — блоками `figure` со ссылками `data-chart` и `data-album` на UUID, без адресов файлов. Адреса, `srcset` и размеры картинок, таблица данных графика и фото альбома подставляются при показе, поэтому смена хранилища не ломает старые статьи. Готовый HTML кешируется по версии статьи; изменение любого альбома сбрасывает кеш вставок.

График автор вводит таблицей прямо в редакторе: строки — подписи, столбцы — ряды значений. Сервер хранит только данные графика (вид, заголовок, подписи и ряды), рисует его фронтенд библиотекой Chart.js: подключаются только столбцы, линии, круговая диаграмма, легенда и подсказки, а сама библиотека загружается при первом графике на странице. Данные графиков статьи приходят в её ответе (поле `charts`). В HTML на месте графика стоит таблица данных: её читают экранные дикторы и браузеры без скриптов, после отрисовки она скрывается визуально. Цвета рядов — CSS-переменные `--chart-color-*` из палитры SCSS.

## Опросы

К статье можно добавить один опрос: один или несколько вариантов с лимитом выбора, необязательная дата окончания, разрешение менять голос, анонимность. Максимум вариантов задаётся в настройках (группа «Публикации»). Голосуют только зарегистрированные, результаты видны всем. В неанонимном опросе у каждого варианта показываются последние проголосовавшие (сколько — в настройках) — одним SQL-запросом с `ROW_NUMBER()` — и полный список по кнопке. Голос пользователя — один бюллетень на опрос (`poll_ballots`, уникальный индекс); варианты, за которые уже голосовали, менять нельзя.

## Альбомы

Альбом — фотографии с описаниями (`/my-albums`), их число задаётся в настройках. Он проходит модерацию и встраивается в статью слайдером или коллажем; оба вида работают без скриптов (горизонтальная прокрутка со `scroll-snap` и сетка). Пока альбом не опубликован, на сайте его нет, а в редакторе автора он остаётся блоком с названием.

## Комментарии и реакции

Комментарии устроены ветками: корневой комментарий и ответы одним уровнем, у ответа на ответ запоминается адресат. Сортировка «популярные» или «новые», ответы подгружаются по кнопке. Писать могут только зарегистрированные; править — автор, удалять — автор или модератор. Удалённый комментарий с ответами остаётся заглушкой.

Реакции — три положительные и три отрицательные, на статьи и комментарии, можно поставить несколько разных. На своё реагировать нельзя. Реакции хранятся в одной таблице с наследованием Doctrine (`SINGLE_TABLE`): `ArticleReaction` и `CommentReaction`. «Рейтинг конфликтности» в админке показывает публикации, где много и положительных, и отрицательных реакций (мера pos·neg/(pos+neg)).

## Жалобы

Пожаловаться можно на статью, комментарий, пользователя и альбом: оскорбление, разжигание ненависти, запрещённый контент, 18+, нарушение авторских прав или другое (с пояснением). Жалобы тоже хранятся с наследованием одной таблицей. Модератор на странице «Жалобы» скрывает материал или отклоняет жалобы; заблокировать по жалобе можно только того, кем модератор вправе управлять. Автоматическое скрытие после заданного числа жалоб включается настройкой администратора и не касается пользователей.

## Просмотры

Страница статьи после загрузки отправляет просмотр на сервер. Боты отсеиваются (`jaybizzle/crawler-detect`), автор не учитывается, от одного посетителя засчитывается один просмотр в сутки. Посетитель хранится хешем IP и браузера с секретом приложения, источник перехода — только доменом. Сырые просмотры нужны для статистики и хранятся заданное в настройках число месяцев: их чистит команда `views:prune`, которую планировщик запускает каждую ночь. Счётчик статьи виден на сайте и в админке.

## Поисковики и соцсети

Содержимое `<head>` собирает бэкенд (`app/Services/Seo/SeoService.php`), фронтенд только выводит готовые теги: title, description, canonical, keywords из тегов статьи, Open Graph с `article:tag` и `article:section`, Twitter Cards, hreflang для языковых версий, коды подтверждения Яндекса и Google и JSON-LD (`spatie/schema-org`: `BlogPosting` для статьи, `WebSite` и `Organization` для главной, `BreadcrumbList` для раздела). Абсолютные адреса строятся от `APP_URL`: при отрисовке на сервере Nuxt обращается к API по внутреннему имени, и адрес запроса для ссылок не подходит.

Заголовок и описание для поисковиков у статей и разделов — встраиваемый объект Doctrine `SeoMeta` (колонки `seo_title`, `seo_description`). Их задаёт модератор в админке; если поля пустые, берутся заголовок статьи и краткое описание или начало текста. Для главной они задаются в настройках, в группе «Поисковики и соцсети», там же включаются Open Graph, Twitter Cards и RSS.

По умолчанию сайт закрыт от индексации: `robots.txt` запрещает всё, на страницах стоит `noindex, nofollow`. Флажок «Закрыть сайт от индексации» в настройках это снимает.

- `/robots.txt` строится из настроек: служебные разделы закрыты, в конце — адрес карты сайта; можно добавить свои строки.
- `/sitemap.xml` (`spatie/laravel-sitemap`) — главная, разделы, опубликованные статьи и альбомы с языковыми версиями. Карта пересобирается каждую ночь командой `sitemap:generate` и по кнопке в настройках (задача `GenerateSitemapJob` в очереди); файл лежит в `storage/app`.
- `/rss.xml` (`spatie/laravel-feed`) — последние опубликованные статьи, их число задаётся в настройках.

Кнопки «поделиться» (ВКонтакте, Одноклассники, Telegram, Facebook, X) — обычные ссылки без сторонних скриптов; адреса готовит сервер, сети включаются в настройках.

## Счётчики и аналитика

Яндекс Метрика, Google Analytics 4, Google Tag Manager, пиксели VK и Meta включаются по отдельности в настройках (группа «Счётчики и аналитика»). Скрипт счётчика загружается только после согласия посетителя на его категорию cookies: Метрика, GA4 и GTM — аналитика, пиксели — реклама. В регионе, где баннер cookies не нужен (США), согласие считается данным. Сайт отправляет цели «registration» (регистрация) и «article_view» (просмотр статьи) и просмотры страниц при переходах.

Страница «Аналитика» в админке показывает отчёты за 30 дней через API: Яндекс Метрика (Stat API, OAuth-токен) и GA4 (Data API, `google/analytics-data`, ключ сервисного аккаунта). Каждый сервис — реализация `AnalyticsProvider`; новый добавляется классом и параметром конструктора `AnalyticsReports`. Токены хранятся как секреты настроек и на фронтенд не попадают; ответы кешируются на час.

## Статистика

Страница «Статистика» в админке (владелец и администраторы) строится по собственным данным сайта за 7, 30, 90 или 180 дней: просмотры и уникальные посетители (боты отсеяны при записи, сырые данные хранятся заданное в настройках число месяцев), регистрации, публикации и комментарии по дням, самые читаемые статьи и источники переходов. Графики рисуют штатные компоненты MoonShine из пакета `moonshine/apexcharts` (`LineChartMetric`).

## Доступность и производительность

- Логику, которую раньше считал браузер, выполняет сервер: ряды фильтра разделов (`/api/sections/filter`), анонсы, ссылки «поделиться», теги `<head>`.
- Шрифты Manrope и DM Sans подключены через `@nuxt/fonts` из Fontsource: файлы скачиваются при сборке и раздаются с самого сайта (`/_fonts`), сторонних запросов до согласия на cookies нет, для каждого шрифта есть метрически подобранная замена.
- Цвета текста подобраны с контрастом не ниже 4,5:1, у полей и кнопок есть видимый фокус, у картинок — `alt`, размеры и ленивая загрузка, диалоги — нативные `<dialog>`.
- Состояние сессии, настройки сайта и баннер cookies отрисовываются на сервере: первая отрисовка не ждёт запросов из браузера.
- Проверка production-сборки (`npm run build`, сервер `.output`) на главной, статьях (в том числе с графиком), входе, регистрации, `/write`, аккаунте, списках автора и формах правки:
  - Lighthouse: производительность 96–99, на страницах с редактором 88–90 (время отклика dev-бэкенда и загрузка TipTap), доступность 100, сдвиг макета не выше 0,004;
  - валидатор W3C: ни ошибок, ни предупреждений, ни информационных сообщений.
- Редактор загружается только в браузере; до загрузки его место занимает блок той же высоты, поэтому форма под ним не сдвигается. Даты выводит `<NuxtTime>`: в HTML с сервера они уже есть, а браузер показывает их в часовом поясе посетителя без расхождения при гидратации.
- В dev-окружении лучшие практики Lighthouse ниже 100 из-за HTTP без HTTPS, а SEO — из-за закрытой индексации (настройка по умолчанию: `robots.txt` с `Disallow: /` и `noindex`) и пустого описания главной в настройках (оно задаётся только в админке). Служебные страницы (`/write`, `/account`, списки автора) закрыты в `robots.txt`, описание им не нужно.

Как повторить проверку (образы `ghcr.io/validator/validator` и любой образ с `lighthouse` и Chromium):

```powershell
docker compose exec frontend npm run build
docker compose stop frontend
docker compose run -d --rm --name nuxt-prod frontend node .output/server/index.mjs
docker network disconnect laravel-doctrine_default nuxt-prod
docker network connect --alias frontend laravel-doctrine_default nuxt-prod
docker run --rm -d --name w3c -p 8888:8888 ghcr.io/validator/validator:latest
```

После проверки остановите `nuxt-prod` и `w3c` и запустите `docker compose start frontend`.

## Устройство кода

- **Слои.** Контроллер → FormRequest (`app/Http/Requests/<Домен>`, проверка и права в `authorize()`) → сервис (`app/Services/<Домен>`) → репозиторий (`app/Repositories`). Запросы к базе — только в репозиториях.
- **Данные между слоями** — DTO `app/DTO/<Домен>/<Имя>Data` (`final readonly`) и коллекции. DTO, которые уходят в JSON, реализуют `Arrayable`; страницы списков — `DTO/Common/PageData`.
- **Ошибки и доступ — штатные механизмы Laravel и Laravel Doctrine.**
  - Записи подставляются в контроллеры привязкой маршрутов (`LaravelDoctrine\ORM\Middleware\SubstituteBindings`); `EntityNotFoundException` отвечает 404.
  - Права — политики `app/Policies` и способности из `Enums/User/Ability`; проверка в `authorize()` FormRequest и middleware `can:`. Скрытые записи отвечают 404 через `denyAsNotFound()`.
  - Ошибки полей — правила FormRequest, стандартный ответ 422.
  - Страницы MoonShine проверяют права в `onLoad()`.
  - Доменная ошибка без привязки к полю — `app/Exceptions/ConsentNotRevocableException` с методом `render()`.
- **События и очереди:**
  - регистрация и смена email → письмо подтверждения (слушатель в очереди);
  - удаление аккаунта → отзыв согласий;
  - новая жалоба → проверка порога автоскрытия;
  - пересборка карты сайта — задача в очереди;
  - настройки почты из базы применяются слушателем перед отправкой.
- **Контракты и трейты** — в `app/Contracts` и `app/Traits`.
- **Стратегии.** Правовые регионы, цели жалоб (`ComplaintTarget`), провайдеры аналитики (`AnalyticsProvider`). Действия модерации и разбора жалоб — перечисления `ModerationAction` и `ComplaintAction`, результат входа через соцсеть — `SocialLoginResult`.
- **Настройки** хранятся только в базе. В `config/services.php` — неизменные адреса внешних сервисов: шаблоны ссылок «поделиться», скрипты счётчиков, адреса API.
- **Фронтенд.**
  - Страница аккаунта собрана из компонентов `components/account/*`.
  - Счётчики — по модулю на сервис в `app/metrics`.
  - Лимиты форм — `useFormLimits()`.
  - Ошибки API — тип `ApiError`.
  - Настройки сайта загружает плагин `site-config` до отрисовки страниц.
  - Стили — SCSS: `app/assets/scss` (части и палитра `_variables.scss`), стили редактора и админки — в `frontend/editor`. Сборка минифицирует CSS.
  - Графики рисует Chart.js (`editor/rich-editor/chart-view.ts`), библиотека загружается только на страницах с графиками.
- **Стиль.** PHP — Pint (`pint.json`). TypeScript и Vue — ESLint (`npm run lint`) и проверка типов (`npm run typecheck`).

После деплоя перезапустите воркеры очереди и сбросьте кеш: воркер держит загруженный код, а формат значений в кеше мог измениться.

```powershell
docker compose exec -u www-data app php artisan queue:restart
docker compose exec -u www-data app php artisan cache:clear
```

## Проверки

Команды artisan запускайте от пользователя `www-data`: если запустить тесты от root, файл журнала станет недоступен php-fpm.

```powershell
docker compose exec -u www-data app php artisan test
docker compose exec app vendor/bin/pint --test
docker compose exec frontend npm run lint
docker compose exec frontend npm run typecheck
docker compose exec app php artisan doctrine:migrations:diff --no-interaction
docker compose exec frontend npm run build
docker compose ps
```

Те же проверки GitHub Actions выполняет на каждый push в `master` и на каждый pull request (`.github/workflows/ci.yml`):

- **PHP — стиль и зависимости.** `composer validate`, Pint и `composer audit`.
- **PHP — тесты.** Сборка ассетов админки, компиляция шаблонов Blade и PHPUnit.
- **База данных.** Сопоставление сущностей, миграции и сидеры установки на чистом PostgreSQL. Если сущности расходятся с миграциями, `doctrine:migrations:diff` создаёт новую миграцию, и проверка падает.
- **Фронтенд.** ESLint, проверка типов, сборка сайта и ассетов админки.

Сброс пароля и восстановление удалённых пользователей в проект не входят.
